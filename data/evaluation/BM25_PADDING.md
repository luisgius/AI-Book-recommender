# BM25 padding: what the zero-score books cost the hybrid (V13)

Generated by `python -m app.evaluation.bm25_padding report` from the rankings of the run of 2026-11-11T18:37:51+00:00 (git `86c5cdc`, device mps).
44 test queries (en 24, es 20), the 177-book collection, depth 10.

## Why

Until V13 the local BM25 adapter returned `max_results` books for every query: rank_bm25 scores every book, and the list was cut without looking at the scores, so books that contain no query term (score 0) filled it. In a hybrid those books enter the RRF fusion as if the lexical side had retrieved them. V12 saw it descriptively (`PROFILE_PARITY.md`). V13 fixed the adapter: it returns only books that contain a query term. The old behaviour stays behind `BM25SearchRepository(zero_score_padding=True)`, used only by the evaluation paths that reproduce published numbers.

## Design (fixed before the run)

Shared harness of V06 (`retrieval_ablation`: `ModelStack`, `make_searcher`, `collect_run`); the `SearchService` is unchanged (RRF k = 60, 2 x 10 candidates per side, 2 x 30 with the reranker, which re-orders the top 30). The published arms run exactly as declared in `retrieval_ablation.SYSTEMS` (legacy padding); the `_nopad` arms are the same systems with the fixed adapter.

|---|---|---|
| `bm25_normalized` | yes | BM25, normalizing tokenizer (accents folded, punctuation split, stopwords removed) |
| `bm25_normalized_nopad` | no | BM25, normalizing tokenizer, fixed adapter: only books with a query term |
| `vec_e5` | - | FAISS, intfloat/multilingual-e5-large-instruct (cosine index) |

Pre-declared contrasts (nDCG@10, system minus reference), one Holm family of three: F1 `hybrid_norm_e5_nopad` vs `hybrid_norm_e5` (Does removing the padding change the hybrid?); F2 `hybrid_norm_e5_nopad` vs `vec_e5` (Is the fixed hybrid at least as good as its vector side?); F3 `hybrid_norm_e5_bge_nopad` vs `hybrid_norm_e5_bge` (Does the fix still matter after the reranker?). Two-sided paired randomisation test (sign flips) and paired percentile bootstrap 95% interval, 10,000 resamples, seed 0. Everything else is descriptive.

Judgments: `app/evaluation/relevance_judgments_extended_v13.json` = `app/evaluation/relevance_judgments_extended_cloud.json` (sha256 e3f82f1878fe...) plus 22 pairs graded by z-ai/glm-5.3-flash for this measurement (22 holes at the start; grades 0/1/2/3: 18 / 4 / 0 / 0; 0.0015 USD). Every returned top-10 result of every system has a judgment. The file has since received 41 more grades by the same judge, for books only the cloud stack returned (`cloud_live_check.py`); they judge no book of these runs but can raise a query's ideal DCG, and the tables here are computed on the file as it is now (1833 judgments, sha256 8eaf6ed626a1...).

## The vector side

`FaissVectorSearchRepository` never pads: it returns at most `max_results` books, each once, fewer when the index or a filter leaves fewer (tests in `tests/infrastructure/test_faiss_vector_search_repository.py`). Dense retrieval has no "no match", though: every book has a cosine, so the nearest ten are returned however far they are. `vec_e5` cosine at rank 1: median 0.863 (min 0.777); at rank 10: median 0.828 (min 0.757, max 0.918), over 44 queries with 10 results.

## Limits

- 44 queries and 177 books: differences below about 0.08 nDCG@10 are hard to detect.
- The added grades come from an LLM judge, not from people.
- The fixed lexical lists are shorter, so Judged@10 is below 1.000 for the BM25-only arm although every returned book is judged.

python -m app.evaluation.bm25_padding run      # models; the judge only for missing pairs
